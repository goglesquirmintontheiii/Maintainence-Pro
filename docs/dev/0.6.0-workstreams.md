## Migrations

The chain is fixed: `0005 → 0006_requests → 0007_messaging → 0008_notifications → 0009_sync → 0010_scan →
0011_platform → 0012_sysadmin`. Write your tables by hand in **your** file only (the foundation left them empty).
Keep ops batch-friendly (SQLite and PostgreSQL), name constraints with `op.f(...)`, and make `downgrade()` undo
`upgrade()`. A migration that needs another workstream's table goes in the later file of the two.

## Shared contracts

**Events (G-05).** Every write calls `emit(...)`. Notifications, realtime and email to outsiders are event
**consumers** (`@consumer("prefix.")` in `mpro/core/events.py`), never direct calls from services. List the event
types you emit, with the `data` keys a consumer can rely on, in your section below so F3 can route them.

**Realtime (F2).** `mpro.core.realtime.publish(org_id, topic, payload, user_ids=None)` and in the browser
`useLive(topic, cb)` / `useLiveInvalidate(topic, queryKeys)` from `lib/live.ts`. Topics: `user:<id>`, `wo:<id>`,
`conv:<id>`, `requests`, `org`. Placeholders exist now; they become real when F2 lands, so call them freely.

**Offline (F4).** `queueMutation({method, path, body, label, idempotencyKey})` and `useOnline()` from
`lib/offline.ts`. Today it sends straight away; F4 makes it queue and replay with idempotency keys.

**Permissions.** The foundation added `requests.*`, `messages.use`, `messages.manage`, `notifications.rules`,
`scan.settings`, `scan.history` and the Requests / Messages areas in `mpro/core/permissions.py`. Add more next to
them if you need to. Every new endpoint gets a cross-org test (G-15).

**Routes and nav.** `/requests`, `/requests/:id`, `/messages`, `/messages/:id`, `/notifications` and
`/mpro-management/*` already point at placeholder pages you replace. Public pages (no login) are added next to
`/quote/` and `/x/` at the top of `main.tsx`.

**Demo data.** Each new module has `demo.py: seed(org, admin)`, already called from `mpro/demo.py`. Keep it
idempotent.

## Testing etiquette

- Run your own tests (`uv run pytest tests/test_<yours>.py`), not the whole suite; the integrator runs everything.
- PostgreSQL: use your own database so you don't clash, e.g.
  `createdb mpro_test_f1` then `TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/mpro_test_f1`.
- `cd frontend && npm run typecheck` (never `tsc -b`, it writes .js files into `src/`).
- Don't commit; the integrator does.

### F5 Scan

All carry `entity_type` / `entity_id` of the scanned record (asset, location, part, work_order, procedure, meter).

- `scan.scanned`: a code was scanned. `data`: `scan_id`, `action` ("scan"), `work_order_id` (work-order codes),
  `user_id` (None for public scans; those events also have no IP and actor "Public scan"), `source`
  (camera | link | typed | photo | public).
- `scan.checked_in`: someone checked in at a location. Same `data`, `action` = "check_in", `work_order_id` if given.
- `scan.recorded`: an action taken after a scan (start_wo, start, complete, reading, use, restock, count, report),
  same `data`.
- `scan.settings_changed` (org), `scan.requirement_changed` (procedure; `changes` on_start / on_complete).

Hooks for others:
- F1: append `fn(org_id, entity_type, entity_id) -> url | None` to `mpro.qr.scan.PUBLIC_REQUEST_URL` so a signed-out
  scan of an asset or location code goes to your portal form. Signed-in "Report a problem" links to
  `/requests/new?asset_id=<id>` / `?location_id=<id>`, and `/scan?for=request` scans then opens that form.
- Work orders: `mpro.workorders.services.START_CHECKS` (new, like `COMPLETION_CHECKS`) blocks moving to In Progress.

### F6 Platform

- `wo.parts_short` (entity `work_order`): Done couldn't take every Planned/Reserved part because stock ran out (MP-131).
  `data.lines`: list of "Part: used X of Y unit (Z short)". Worth a notification to whoever completed it and the
  parts team.
- `wo.part_status` summaries now read Planned / Reserved / Used (Kitted and Staged are gone).
- `purchase_order.vendor_acknowledged`, `purchase_order.vendor_proposed_date`, `purchase_order.vendor_declined`
  (entity `purchase_order`, no actor: the vendor answered through the emailed link, r261). `data`: `response`,
  `responder_name`, `proposed_date` (YYYY-MM-DD or null), `note` (first 500 chars), `vendor_id`. Notify the PO's
  requester and approvers; a decline or a proposed date later than `due_on` deserves attention.
- Part edits that change the picture include `changes.picture` on the existing `part.updated` event.

### F7 Sysadmin

All carry `data.sysadmin = true`. Server-level events have `org_id` None (the server audit log, shown in MPro
Management); events about one organization use that organization's id so they show in its audit log too.
Notifications don't need to route any of these.

| Event | org_id | Entity | `data` keys |
|---|---|---|---|
| `sysadmin.added` / `sysadmin.removed` | None | user | `via` ("terminal", "MPro Management", "create-admin", "demo data"), `forced`, `first` |
| `sysadmin.password_check_failed` | None | user (the sysadmin) | – |
| `sysadmin.user_updated` / `user_locked` / `user_unlocked` | None | user | changes: name, email, phone, active |
| `sysadmin.user_password_reset` | None | user | `mode` ("email" or "set") |
| `sysadmin.server_settings_changed` | None | server/settings | `restart_needed` (labels); secrets shown as ••• |
| `sysadmin.api_key_created` / `_updated` / `_deleted` | None | api_key | `service` (create) |
| `sysadmin.org_updated` | org | org | changes: name, email, plan |
| `sysadmin.membership_added` / `_changed` / `_removed` | org | user | `role`, `org` |
| `sysadmin.org_deleted` / `sysadmin.org_restored` | org | org | – |

Other workstreams: `mpro.sysadmin.services.secret_for(service)` returns the newest API key for "openai",
"anthropic", "google", "azure_openai", "ollama" or "other", decrypted (None if there's none).
